Technical Writing & Export Agent

An AI-assisted tool that checks engineering writing against the group's standards and assembles finished documents in the firm's official templates.

My role
Proposed it, led the original intern team, and built the current version.
Result
In use in SSR's Civil/Environmental group, with more of the group starting.
Status
In use

Challenge

Engineering documents have two separate problems: is the writing right, and is the document put together right? Both take experienced people's time.

Origin

In Summer 2026 I proposed the concept and was selected as project manager for an eight-person, cross-disciplinary intern team that built the first version.

What I built

  • A writing agent that reviews drafts against the group's style standards and suggests rewrites that keep the technical meaning.
  • An export agent that guides the user through what a document needs and produces it in the correct official template, as Word or PDF.
  • Checks for consistency before anything is exported.
  • The current version adds template routing, guided intake, document extraction, and AI-ready template workflows, with Word/PDF output.

Where it is now

After the internship I kept developing it, focused on SSR's Civil/Environmental group as a realistic place to put it to work. It is now in use in the group, and more people are starting to use it.

What I learned

The hard part isn't the AI. It's understanding exactly how engineers write and assemble documents, and building something that fits that process instead of adding steps.

Tools & methods

  • JavaScript
  • Claude API
  • Prompt engineering
  • Word & PDF generation
  • Playwright testing

Purpose

To work through, from a civil engineering point of view, how a stadium site is chosen and what the site needs before a building can go on it.

What I did

  • Researched built precedent venues and defined engineering screening criteria.
  • Compared candidate sites and carried a preferred site forward.
  • Developed conceptual site layout, grading, utilities, and the permitting path at a feasibility level, working with a GIS specialist on the mapping.
  • Built the deliverable as an interactive report with zoomable plan exhibits.

What I learned

How tightly site selection, grading, utilities, and permitting constrain each other, and how much of a venue's success is decided before design starts.

How I work

The same sequence runs through my SSR work, the AI Training Hub at UTK, and the tools I'm building now.

  1. Learn the workflow

    Do the work first: coordinate the drawings, write the reports, sit in on the process.

    For example: About 615 valve records coordinated at SSR

  2. Find the repetitive part

    Separate the searching and re-typing from the decisions that need an engineer.

    For example: Cross-referencing valves across drawing sets

  3. Respect the judgment

    Design tools that surface evidence and leave the call to the engineer.

    For example: The Export Agent suggests rewrites; the engineer decides

  4. Prototype

    Build a working version quickly and test it against real documents.

    For example: Technical Writing & Export Agent

  5. Refine with engineers

    Put it in front of the people who do the work and improve it from their feedback.

    For example: Now in use in SSR's Civil/Environmental group
